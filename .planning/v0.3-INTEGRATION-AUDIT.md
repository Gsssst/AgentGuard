### Deliberate non-connections

- Phase 1 `Router` and Phase 3 `LoopGuard` are not invoked by
  `GuardedToolNode`; LangGraph owns graph routing, while this adapter owns only
  tool execution. This is consistent with the v0.3 scope, but it means loop
  termination/reliability reports are not automatically applied to a LangGraph
  graph.
- Phase 4 `CheckpointStore` is not used by the adapter. LangGraph's checkpointer
  is the stated owner of graph state and interrupt recovery. This is correct
  for the declared architecture and avoids two competing checkpoint systems.
- There are no HTTP/API routes or frontend/auth surfaces in v0.3; API-consumer
  and auth-protection checks are therefore not applicable.

## End-to-End Flow Status

### Flow A — direct multi-tool execution (no approvals)

`AIMessage.tool_calls` → `GuardedToolNode.prepare()` → per-call validation →
`Runtime.execute_explicit_batch()` → permission check → resource lock →
timeout/retry executor → `ToolResult` → ordered `ToolMessage` list.

Deterministic and real LangGraph smoke tests cover this path, including
concurrency, lock conflicts, timeout, retry exhaustion, cancellation, unknown
tools, and missing guards. **Status: WIRED/PASS.**

### Flow B — approval interrupt/resume (two-node graph)

`prepare` executes allowed calls and persists a projection → `approval` sends
one redacted `interrupt()` payload → LangGraph `MemorySaver` persists state →
`Command(resume=decision_map)` → per-call normalization/digest check → approved
subset through Runtime explicit batch → ordered `ToolMessage` results.

Real StateGraph tests prove matching `thread_id`, partial approval, digest
mismatch isolation, missing-tool handling, and no replay of direct work in the
tested two-node composition. **Status: WIRED/PASS for the tested composition.**

### Flow C — approval graph with the standard LangGraph message reducer

Using `MessagesState` (whose `messages` field uses `add_messages`),
`prepare()` writes placeholder `ApprovalRequired` messages before interrupt;
after resume, `approval()` writes final messages. The reducer appends rather
than replaces, producing duplicate `ToolMessage` entries for the same
`tool_call_id`:

```text
pause:  [AIMessage, ApprovalRequired(write-1)]
resume: [AIMessage, ApprovalRequired(write-1), success(write-1)]
```

This is a common LangGraph state shape and violates the expected one-result per
input-call contract in the resumed flow. **Status: BROKEN — BLOCKER B1.**

## Findings

### BLOCKER B1 — approval resume duplicates messages with `add_messages`

**Affected requirements:** APPROVAL-03, APPROVAL-06; indirectly BATCH-04.

**Break:** `GuardedToolNode.prepare()` returns `{"messages": output}` where
pending calls are represented by placeholder `ApprovalRequired` messages.
`GuardedToolNode.approval()` later returns final messages. With LangGraph's
standard `add_messages` reducer, both updates are appended. The phase tests use
a plain `TypedDict[list]`, so they do not detect this reducer-specific break.

**Impact:** A normal LangGraph `MessagesState` graph receives duplicate tool
results after approval. Downstream model/tool routing can observe stale
`ApprovalRequired` output and an additional success/denial output, so the
end-to-end approval flow is not correct for the common integration shape.

**Required follow-up:** Change the preparation/approval state contract so
preparation does not append user-visible `ToolMessage` placeholders (or use a
documented replacement strategy), and add a real `MessagesState` +
`add_messages` interrupt/resume regression test. Do not claim this is fixed by
the existing plain-list tests.

### WARNING W1 — requirements traceability is stale

`REQUIREMENTS.md` still marks BATCH-01..05 and APPROVAL-01..06 as unchecked and
its traceability table says Pending, while Phase 8/9 verification reports and
the implementation provide test evidence. This is documentation drift, not a
runtime break, but it can cause a milestone audit or release checklist to
incorrectly report incomplete requirements.

### WARNING W2 — adapter approval/validation outcomes are not fully audited

Allowed calls emit Runtime action/tool/batch events, and post-resume execution
emits approval grant/deny events. However, `prepare()` does not emit an
`APPROVAL_REQUESTED` event for pending adapter calls, and immediate unknown,
malformed, or missing-guard failures are converted directly to `ToolMessage`
values without a corresponding Runtime event. `ReliabilityReport` also expects
a terminal `RunResult`/`RUN_FINISHED` event, which adapter invocations do not
produce. The result messages are safe, but an event-sink consumer cannot obtain
a complete approval audit timeline from the adapter alone.

**Affected requirements:** ADAPTER-05 (audit boundary) and the project Core
Value's explainable evidence goal. This is a warning because the phase's
explicit Tool execution and failure-message requirements still work.

### WARNING W3 — sensitive original arguments are retained in graph state

The human-facing interrupt payload is recursively redacted, but
`_agentguard_prepared.pending[*].arguments` retains original arguments so the
digest can be recomputed. LangGraph checkpointers therefore persist raw
arguments in the graph state even though they are absent from the interrupt
JSON. Durable encryption/remote approval storage is explicitly out of scope,
but this should be called out in integration/security documentation before a
public release.

### WARNING W4 — historical phase verification artifacts are absent

No `VERIFICATION.md` exists for Phases 1–6; their SUMMARY files contain
self-checks and test counts, but not the standardized verifier reports used by
Phases 7–9. This weakens retrospective milestone evidence and makes it harder
to prove cross-phase regressions were checked. It is not itself a runtime
failure; regenerate phase verification reports if release evidence requires
uniform artifacts.

### WARNING W5 — compatibility evidence is intentionally narrow

The tested optional stack is exactly `langgraph==0.6.11` and
`langchain-core==0.3.86` on Python 3.12.9. No broad historical/future version
matrix is wired or promised. This is consistent with COMPAT-03/05 and the
documented v0.3 boundary, but consumers must pin the same versions.

## Technical Debt and Explicit Limits

- Process-local resource locks and local in-memory event sinks/checkpoints;
  no distributed coordination or HA.
- At-least-once/replay semantics; no exactly-once external side effects.
- No reviewer identity, RBAC/ABAC, remote approval service, frontend console,
  or multi-round pending workflow.
- No dependency-aware DAG scheduling for tool calls.
- LangGraph compatibility is bounded to the verified package versions.
- Adapter does not automatically apply Phase 3 loop detection or produce a
  terminal `ReliabilityReport` for a graph run.

## Overall Verdict

The core Phase 1→2→5→6→7→8→9 execution chain is substantially wired and has
strong deterministic/real test evidence. The milestone is **not fully
integrated yet** because the canonical LangGraph `MessagesState` approval flow
has a reproducible duplicate-message blocker (B1). Resolve B1 and add the
regression test before declaring v0.3 release-ready; then reconcile the stale
requirements statuses and decide whether to regenerate Phase 1–6 verification
reports for uniform evidence.
